## 移動時に守る手順

1. [機械可読の移動案](workspace-move-plan.jsonl) の各パスを絶対パスへ解決し、移動元が指定の親フォルダー内、移動先が開発本体内に収まること、移動先が存在しないこと、衝突・循環・長すぎるパスがないことを確認する。移動対象を使用中のアプリや作業があれば終了を待つ。
2. `画面試作` は `codex/management-ui` のGit worktreeで未コミット変更がある。通常のフォルダー移動ではなく `git worktree move` を使い、作業中の変更・未追跡ファイル・`.venv` リンクを保持して移動前後のGit状態を比較する。内容を本体へ混ぜたり、未コミット変更を一括コミットしたりしない。
3. `配布サイト` は別GitリポジトリでSites設定を持つ。Gitと設定を一式保持する。移動時はSitesスキルの手順とパス参照を確認し、ローカル整理だけを理由にサイトを再公開しない。Codexの保存済みプロジェクトは現在開発本体を指しており、その場所は維持する。
4. `AGENTS.md` のサイトパス、`docs/UI_WORKFLOW.md`、`docs/STATUS_AND_ISSUES.md` の試験結果リンク、`docs/DISTRIBUTION_VERIFICATION.md` の検証記録パス、`docs/UPDATE_GUIDE.md` の配布先を実際の移動後に合わせる。`tools/build_windows_distribution.py` の既定出力先も本体内へ変更し、古い兄弟フォルダーを再生成しないようにする。
5. 検証用スクリプト、起動情報、ショートカット等の旧絶対パス参照を確認する。過去の結果JSONは検証時点の証跡として保持し、移動対応表から追跡できるようにする。移動を口実に実請求の再取得や通常台帳への試験書込みを行わない。
6. 各移動の成功を記録し、逆方向の復元計画を残す。移動前後のファイル数・バイト数・リンク・Git状態を比較する。途中で失敗した場合は上書き・削除・コピーへの切替えで進めず、成功範囲と未完了範囲を記録する。
