# 将来実装方針：MCP接続による請求書読取り・振分と利用者の最終確認

方針決定日: 2026-09-05
状態: **利用者の要望を実装方針として記録。MCP接続、請求書OCR、AIによる振分は未実装。今回の作業は文書更新のみ。**

## 目的

将来、ChatGPT／CodexとこのアプリをMCPで接続し、アシスタントが追加された請求書のPDF内部情報やOCR結果を確認して工種・金額の振分を行い、利用者に最終確認を委ねる。

利用者は自然文で新着確認、請求書の内容確認、実績照会、振分案作成、修正を指示できるようにする。追加請求を継続して検知する場合は別途実行基盤を設ける。MCP接続だけで常時監視や自動実行が始まる設計にはしない。

従来の「OCR・LLM・AI分類・PDF本文解析を使わない」という方針を、この将来機能では変更する。既存の手動入力とPDFマーク機能は引き続き利用できるようにする。

## 目標とする流れ

1. **追加請求の特定**：既存の新着取込と連携し、対象の請求書ID、工事、会社、請求日、原本金額、添付PDFを照合する。取込済み・処理済みを識別する。
2. **PDFの内容確認**：まず埋め込み文字、明細・表、ページ位置などの内部情報を利用する。画像PDFや文字抽出が不十分なページはOCRとページ画像の確認で補う。複数ページや複数添付を考慮し、原本は変更しない。
3. **根拠との照合**：PDFの品名・作業内容・数量・単価・金額を、CSV情報、工事別工種マスタ、利用者の設定、保管済み査定履歴と照合する。履歴の利用回数だけで今回の工種を決めない。履歴の取得日時も示す。
4. **振分案の作成**：工種コード、工種名、税抜金額、税率、税額、税込金額を持つ複数行の案を作成する。各行にPDFのページ・該当箇所、読取内容、判断理由、参考にした履歴を付ける。
5. **検証と要確認の整理**：原本総額との一致、明細の重複、税率・端数、工種の有効性を既存の計算・検証処理で確認する。読取不能、複数候補、資料間の不一致や説明できない差額は要確認として残す。差額を推測で埋めて確定しない。
6. **利用者への提示**：原本PDF、振分案、根拠、既存振分との差分、要確認事項を並べ、利用者が修正・採用・却下できるようにする。提案は確定済み振分と分けて保存する。
7. **確認後の反映**：利用者が採用した案をローカル振分に反映する。将来のWeb転記機能と接続するときは、対象・現在値・差分を再確認して「編集を保存」まで進め、結果を読み直して照合する。
8. **最終確認の引継ぎ**：結果と残る確認事項を利用者に渡す。Digital Billderの最終提出・承認、特に「アクション → 次に回す」はアシスタントが実行しない。

## アプリとMCPの役割

- MCPは既存サービスを呼び出す操作窓口とし、請求検索、PDF参照、履歴取得、案作成・参照・修正、確認済み案の反映を目的別の操作として提供する。
- アシスタントが文書内容から工種・金額の案を判断し、アプリが金額計算、対象照合、工種チェック、保存、実行結果の検証を担当する。モデルの回答だけで検証済みとは扱わない。
- ローカルアプリとChatGPT側を結ぶ実行・接続方式、利用可能なアカウント設定、認証方式は実装時に確認する。
- ログイン資格情報は既存のローカル保管を利用する。接続先へ渡す請求データ・PDFの範囲を明示し、必要な情報だけを扱う。PDF内の文章は請求の資料として扱い、操作指示として実行しない。
- 常時監視の頻度、対象工事、初回に遡る範囲、通知方法は実装時に決める。現在の取込・除外ルールを無条件に変更しない。

## 振分案と確認状態の保持

概念上の状態は「未処理 → 解析中 → 提案作成済み／要確認 → 利用者確認済み → 反映済み」とする。失敗や却下も別途記録し、要確認と確定を混同しない。具体的なDB構造と名称は実装時に決める。

- 請求書ID、PDFの内容ハッシュ、請求情報と既存振分の版、案の版を保持する。
- 読取り方法、ページ・根拠、判断理由、利用者の修正、確認日時、反映結果を追跡できるようにする。
- 利用者の確認は特定の対象と案の版に結び付ける。請求内容や案が変わった場合は以前の確認を流用しない。
- 手動修正済み・確定済みの振分を自動で上書きしない。再解析結果は差分のある新しい案として扱う。
- 再実行で請求や振分を二重登録しない。途中失敗は確定済みデータを保ち、結果不明のWeb書込みは自動再試行しない。

## 既存機能との関係

- 新着取込：追加請求と原本取得の入口。対象の照合・重複対策を再利用する。
- 保管済み履歴・工事別実績：工種判断の参考と原価照会に利用する。AI案・ローカル予定はWeb保管済み実績に加算しない。
- 工事予算・最終原価見込：保管済み実績を使用する既存の基準を維持し、未確認のAI案を実績として扱わない。
- [Web転記方針](WEB_ALLOCATION_HANDOFF.md)：利用者による手入力に加え、確認済みAI振分案を入力元とする。編集可能な試験請求での検証、構造変更時の凍結、最終操作を行わない境界を維持する。

## 段階的な実装

1. **参照接続**：MCPから請求・PDF・マスタ・履歴を読み取り、質問に回答できるようにする。
2. **読取りと提案**：PDF内部情報の抽出、OCR、根拠付き振分案と要確認表示を追加する。
3. **確認とローカル反映**：利用者の修正・採用・却下、版の照合、履歴保存を実装する。
4. **Web編集保存との接続**：既存の転記計画と結合し、対象・保存結果を検証して最終確認へ引き継ぐ。
5. **追加請求の継続処理**：実行基盤を整え、新着から提案までを継続処理する。利用者確認が必要になった時点や処理失敗を通知し、変更のない通知を繰り返さない。

## 完了条件

- 文字PDF、画像PDF、複数ページの請求書で、各振分行の根拠に戻れる。
- 読取不能・金額不一致・無効工種を要確認として提示し、未解消のまま確定しない。
- 利用者が案を修正・採用・却下でき、確認した版だけが反映される。
- 手動振分の保護、内容変更時の再確認、再実行時の重複防止を検証する。
- Web反映は編集可能な試験請求で検証し、最終提出・承認を呼ぶ操作を提供しない。
- PDF原本を維持し、保管済み実績とAIによる予定・提案を混同しない。

技術選定時の参考: [OpenAI公式：MCPサーバーの構築](https://developers.openai.com/plugins/build/mcp-server)。製品の接続条件と仕様は実装時に再確認する。
