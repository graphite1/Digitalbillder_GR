# 2026年9月5日〜6日の開発環境の変化と評価

記録日: 2026-09-06。対象: Digitalbuilder GRの開発本体、Windows試験環境、配布・更新の運用。機能と公開状況は本書作成時点の記録であり、以後の最新情報は [現状と課題](STATUS_AND_ISSUES.md) を参照する。

## 総合評価

**個人で継続開発するための基盤が大きく整った。特に、変更を作る・別環境で確かめる・利用者へ届けるという流れを、実際に検証できるようになった点が大きい。**

以前から存在したテストや更新機構に、空のWindowsでの導入試験、配布物の不具合修正、旧版からの更新検証が加わった。道具の数だけでなく、問題を発見して原因を絞り、修正を確かめる能力が向上したと評価する。

## 何が変わったか

| 項目 | 変化 | 理由・メリット |
| --- | --- | --- |
| 作業場所 | 開発本体を拠点とし、補助作業を本体内の `作業補助/` に集約 | 修正する場所と検証記録の所在が明確になり、別コピーへの誤編集を減らせる |
| 初回導入試験 | Windows Sandboxで、初めて使うPCに近い状態を再現 | 開発PCに既にある部品に依存して動いてしまう問題を発見できる |
| PDFの配布不具合 | Sandboxで不足DLLを特定し、アプリ専用の実行環境へ同梱 | 共有DLLを上書きせず、PDF表示と他アプリとの共存を確認できた |
| 開発版の起動 | 開発本体の起動入口を修正し、画面タイトルに「【開発本体】」を表示 | 旧公開版が起動して変更が見えない問題を解消し、起動先を判断しやすくなった |
| 自動テスト | 合成台帳と実際のTk画面部品を使う検証を拡充 | 実請求を書き換えず、金額・工種・中断・検索条件などを確認できる |
| 配布・更新 | v1.0.5を署名付きで公開し、公開ファイルによる旧v1.0.4からの更新を検証 | 配布物の一致、更新前バックアップ、起動、台帳の保持を確認できた |
| 作業分担と記録 | 独立した実装・検証・レビューを分担し、結果を主担当が統合 | 中断と完了の競合など、実装者だけでは見落としやすい問題を検出できた |

## 環境の役割を区別する

- **開発本体**: ソースコードを修正して動作を確認する場所。専用の `.venv` はPythonとライブラリを分ける仕組みであり、Windows全体や台帳を隔離するものではない。
- **Windows Sandbox**: 終了すると状態が消える試験用Windows。初回導入や部品不足の再現に使用する。
- **合成台帳による隔離試験**: 実請求を使わず、金額・日付・更新前後の内容を比較する試験。Sandboxでの試験とは別に実施する。
- **配布版**: 署名と検証を経て利用者へ届ける版。開発本体の最新変更が、直ちに配布版へ入るわけではない。

開発本体の通常起動は従来の台帳保存先を維持し、起動前にバックアップする。開発版の表示が付いたことだけで、実台帳から完全に隔離されたと判断しない。

## 確認済みの成果と残る範囲

| 項目 | 確認済み | 残る範囲 |
| --- | --- | --- |
| 空のWindowsへの導入 | 公開v1.0.4-r2の導入・PDF描画、候補版での共有ランタイム共存・再導入保護 | あらゆる社内PC・端末構成を検証したわけではない。v1.0.5の空Sandboxでの新規セットアップ実行は未実施 |
| v1.0.5への更新 | 公開ファイルを取得し、旧v1.0.4の合成台帳から準備・適用・バックアップ・起動・データ保持を確認。手動更新ZIPも照合済み | 利用者が起動中の仮想環境で行う手動試験の結果は、本書作成時点では未受領 |
| 自動テスト | v1.0.5時点で全体320件成功。公開後の工事別検索候補修正は関連26件成功 | テスト件数は業務全体の正しさや全画面の使いやすさを保証する数字ではない |
| 仮想PC | Sandboxは稼働・試験済み。Hyper-Vは機能を有効化済み | 永続的なHyper-VゲストOSの導入と、その環境での更新・復旧試験は未完了 |
| 実際の業務操作 | 一覧・振分・処理状況・中断などのローカル機能を改善 | 編集可能な請求を用いたWeb保存の実機検証は残る。Web編集保存は無効のまま、上位者への送信は自動実行しない |

公開済みv1.0.5のファイルは差し替えない。選択工事に存在する取引先・請求月・請求日だけを候補にする修正は、開発本体へ反映済みだが次の更新分として扱う。

## 今回の反省と今後の確認方針

「修正したのに画面が変わらない」問題では、開発フォルダーの起動入口が内部で旧v1.0.4を選んでいた。支援側が実際の起動先を確認せず、再起動だけを案内したことも原因だった。

今後は、ソースコードのテストに加えて、利用者が開く起動入口、実際に動く版、台帳の保存先、画面での見え方を対応付けて確認する。報告では「開発本体に実装済み」「配布済み」「利用者環境で確認済み」を区別する。

実装・検証の分担は有効だが、誰がどのファイルを変更し、どの状態を検証したかの管理は必要である。主担当が差分と検証結果を統合し、区切りごとにコミット・プッシュする運用を維持する。

## 次に重視したいこと

以下は優先度の評価・提案であり、新たなツール導入や機能実装を完了したという記録ではない。

| 優先度 | 内容 | 期待する効果 |
| --- | --- | --- |
| 最優先 | 普段の請求確認・振分・検索で使い、不便や誤解が出る箇所を修正する | 実務に合った操作に近づける。今回の工事別検索候補の指摘が具体例 |
| 高 | 実行版と配布版の確認、公開ファイルによる更新試験を定着させる | 「直したつもり」「違う版を確認していた」を減らす |
| 高 | 既存のテスト・配布手順を再利用し、検証の自動化と依存関係の再現性を改善する | 確認漏れや環境差を減らす。CI等の導入状況は別途確認して判断する |
| 条件が整い次第 | 編集可能な試験請求で、Web読取り・保存前後の照合を検証する | 実データの構造と業務上の到達点を確かめる |
| 必要時 | 新しいプラグインや専用スキルを導入する | 既存の道具で足りない具体的な課題がある場合に限定する |
