# 今後の課題：工種振分をDigital Billderへ転記し、最終提出・承認前で止める

作成日: 2026-09-05
状態: **ローカル税率入力・転記プレビュー・Web現在値の読取り・差分表示・凍結ガードを実装。Web書込みは編集可能な試験請求待ちで無効。**

## 1. 目的と今回の指示

ローカルアプリで入力した請求書の工種コード別振分を、Digital Billderの対応する請求へ転記する。
利用者が最後に内容を確認し、提出・承認を自分で行える状態までを自動化することが目標。

当初の文書化指示の後、利用者から実装開始の指示を受けた。書込み前に必要なローカル機能と読取り機能を実装している。
現在の請求は支払済みのため、利用者が月曜日に試験用請求の作成可否を確認する予定。

利用者との合意: **工種・金額を入力して「編集を保存」まで。「アクション」タブの「次に回す」は実行しない。**
既存振分は差分を表示し、無条件に上書きしない。税率は10%が初期値で、8%・非課税も選べる。

## 2. 目標とする利用フロー

将来の入力元として、[MCP接続によるPDF内部情報・OCRからのAI振分案](MCP_INVOICE_ALLOCATION_PLAN.md)を追加する方針。以下の手動入力に加え、利用者が確認・採用した案を転記に接続する。MCP・OCR・AI振分は未実装で、最終提出・承認を利用者が行う境界は維持する。

1. 既存の新着取込で請求書を台帳へ取り込む。
2. 利用者がアプリの請求詳細で工種コードと税抜金額を振り分ける。
3. アプリ内で転記内容と検証結果を確認する。
4. 対象請求のWeb画面を開き、請求書ID・請求内容・編集可能状態を照合する。
5. 対応が確定した入力欄へ工種コードと金額を転記する。
6. Webから入力結果を読み直し、予定した内容との一致を確認する。
7. 「編集を保存」まで実行し、保存後にWeb値を再読込して確認する（現在は試験待ち）。
8. 最後の提出・承認は利用者が行う。

通常操作をブラウザ非表示で進められることが望ましい。
ただし、最後の確認画面の渡し方は、Web側の保存方式を確認してから決める。

## 6. 転記データの対応案

以下は設計案であり、編集画面の仕様を確認して確定する。

| ローカル | Web候補 | 初期方針 |
| --- | --- | --- |
| `invoices.external_id` | 対応する請求詳細 | IDを主キーとして照合する。実際の一覧リンクとの対応を確認する |
| 工事・取引先・請求日・原本額 | 請求基本情報 | 転記前の照合に使用する。変更しない |
| `work_type_codes.code` | 査定入力の工種 | コードの完全一致で選ぶ。名称だけで推測しない |
| `invoice_allocations.amount_excluded` | 査定入力の税抜金額 | 円単位の整数として扱う |
| `sort_order`, `id` | 振分行の順序 | ローカルの表示順を維持する |
| `memo` | 摘要 | 初期の対象には含めない。転記が必要か別途確認する |
| `tax_rate`・税込額と税抜額の差 | 税率・消費税額 | 行別に10%・8%・非課税を保持。税額・税込額を表示。Webの端数規則は試験時に照合 |

既存の請求全体の税抜換算・一部帳票には10%前提が残る。請求詳細で「税抜・10%換算」と明示し、振分の残額と転記検証は税込原本額で比較する。
既存の税込値は移行時に変えない。振分行の税率を変更すると税抜額から再計算する。既存端数との差がある場合は転記プランにエラーを表示し、自動補正しない。

## 7. 実装の進め方

### 第1段階：読み取り調査

1. 対象請求を特定し、編集状態・権限・最終操作を確認する。
2. 編集画面のラベル、入力欄、行追加、保存操作を記録する。
3. 自動保存の有無を確認する。保存の境界が判明するまで実データの入力は行わない。
4. この文書の未確認点と対応表を更新する。

### 第2段階：アプリ内の転記プレビュー

Webへ書き込まずに、対象ID・工種コード・税抜金額・検証結果を一覧にする機能から着手する。

検証項目:

- 振分行があり、工種コードと金額が揃っている。
- 未振分・超過・負の金額など、未対応の状態がない。
- 合計額が対象請求と整合し、税率・端数の条件を満たす。
- Webの請求ID、工事、取引先、請求日、原本額が一致する。
- Web側の編集状態とローカルデータが、確認開始時から変わっていない。
- Webに転記先の工種が存在し、必須項目を満たせる。

### 第3段階：1件の転記と結果照合

1. 最終操作から独立した転記処理を作る。
2. プレビューした内容が変わっていないことを確認して入力する。
3. Web側の工種・金額・行数を読み直して一致を検証する。
4. 許可した範囲で下書き保存し、保存結果を再読込して確認する。
5. 最終提出・承認は実行せず、利用者へ引き継ぐ。

初期実装は1請求ずつを対象にする。複数請求の一括転記は別課題とする。

### 第4段階：確認画面への引継ぎ

- 下書き保存ができる場合: 保存を検証したあと、対象請求の確認画面を利用者へ案内する。
- 未保存の入力を残す場合: その入力を保持したブラウザセッションを利用者へ渡せる方式が必要。
- 非表示ブラウザで入力した未保存内容は、別のブラウザで同じURLを開いても引き継がれない。
- ヘッドレスブラウザを終了すると入力状態が失われるため、既存の `export_session` の寿命をそのまま使用しない。

### 第5段階：失敗・再実行への対応

- Webへの入力は複数操作に分かれるため、途中まで反映される可能性がある。
- 通信切断やタイムアウト時は「未更新」と断定せず、結果不明として再読込・照合を行う。
- 同じ操作を再実行しても行を追加し続けない。既存値と予定値を比較して判断する。
- 既存の入力値が異なる場合、無条件に上書き・削除しない。
- ローカルDBのトランザクションでWeb側の更新を取り消せるとは考えない。
- ローカル振分の変更後は、過去の転記済み判定をそのまま使わない。

### 構造変更を検知したときの凍結

`web_allocation_guard.py` は操作区域・役割・ラベル・入力形式・要素の一意性と数・対象請求IDを各書込みの直前に照合する。
不一致や読取り失敗、書込みの結果不明では `web_allocation_guard` テーブルへ凍結を永続化する。アプリ再起動で解除せず、自動リトライもしない。
許可操作は入力・行追加・編集保存だけ。最終送信は許可リストに含めない。
現在は `APPROVED_CONTRACT = None` で、実際の編集画面の構造が未承認のため、Web保存ボタンを無効化している。
ガードは模擬画面で検証済みだが、実機での構造監視・書込みへの接続は試験請求で行う。凍結中もローカル編集・読取り・差分確認は利用できる。
解除は構造を調査して契約を更新し、回帰テストと実機確認を終えてから開発者が行う。利用者向けの無条件解除ボタンは設けない。

転記の記録が必要な場合は、取得用の `digital_billder_seen` とは別に管理する。
候補項目は、請求ID、振分内容のハッシュ、転記前のWeb値、実行日時、検証結果、保存状態。
認証情報は記録しない。状態名やDBテーブルの追加は未決定。
