## 工種入力を3桁・処理を実績側の正式コードへ対応（2026-09-06）

- 状態: 開発本体で実装・検証済み。公開Windows版v1.0.4-r2には未収録。
- 基本ルール（2026-09-06利用者指定、同日追加実装）: 今回扱う工種コードは原則「D（土木）＋数字3桁」。入力は数字3桁（例: `513`）。対象工事の実績に対応コードがなければ、登録済み数字／D付き工種マスタの名称を使って `D513` として保存できる。実績に別の正式コードがあればそちらを優先する。
- 初期テンプレート40件もD付きに更新。数字入力・予算原本の数字コードの名称補完を維持する。既存の数字マスタがある工事には初期化だけで重複Dマスタを追加せず、既存ID・手修正名称・無効状態を保つ。数字もDもない新規工事にはD付きで登録する。
- 見え方: 保存前に「実績で確認済み」または「D＋3桁の基本ルール（実績未確認）」とコード・名称を表示し、由来を区別する。未登録で名称も不明な番号は先に工種マスタへの登録が必要。複数の接頭辞候補がある場合は自動決定しない。
- 振分入力: 数字入力／候補選択に対応し、保存前に正式コード・実績側の名称を表示する。保存時は正式コードのマスタIDを使う。既存の数字マスタや他の振分を一括変更・統合しない。既存正式マスタの名前・並び順も上書きしない。
- 既存の数字振分: Web転記プレビューでも同じ対応処理を使う。基本ルールによるD対応はコードエラーにしない。未登録・同じ数字に複数の正式コード・無効化されたコードはエラーとし、転記可能と扱わない。Web書込みは引き続き無効。
- 予算: 「Web工種対応」の明示入力も3桁から正式コードへ変換する。予算原本コード・未設定行・既存の保存済み対応を自動で変更しない。
- 確認範囲: 保存済み履歴を読取り専用で照合済み。最新Web画面や未使用工種を含む正式マスタ全件は取得していない。基本ルールによる登録は利用者指定の運用であり、Web上で利用可能と実機確認したことを意味しない。
- 検証: 全体テストに加え、履歴なしのD付きテンプレートから3桁で保存、実績の別接頭辞優先、曖昧／未登録／無効拒否、正式マスタ再利用・旧データ保持・失敗時取消を合成DBで確認。実台帳への書込み・Web送信は行っていない。

### 実装前に決めること

- **送信済み・承認済み・保管済みは同一視しない。** 現在の実績集計は保管済み履歴が対象であり、上位者への送信完了と同じ状態かは未確認。状態の対応関係とアプリ内での計上条件を確認してから接続する。
- 送信完了の確認をWebの読取りで行うか利用者の確認記録で行うかは未決定。今回の構想は自動送信・自動承認・自動検知の実装を意味しない。
- 送信後の修正・取消・差戻しが起きた場合の扱いと、既存の保管済み実績との重複防止を設計する。アプリ内で実績に計上することと、上位者が承認したことを区別する。
- 最終着地予想は、反映した実績だけで自動確定するものではない。現行の残工事見込の入力と、未入力・未確認値を未確定として示す扱いを維持する。
- アプリ内の原価・予算管理は引き続き対象とする。OBIC7関連を保留しても、アプリ内の金額の正確さを後回しにする意味ではない。

### 請求月ルールの個人設定（実装予定・2026-09-05利用者指定）

- 要望: 現在固定されている請求月の判定ルールを、利用者本人がアプリの設定から変更できるようにする。今回は予定への追加のみで、設定画面や判定処理の変更は行っていない。
- 現行仕様: 請求日が前月10日〜当月9日の請求を当月分とする。取込日や送信日は判定基準ではない。取込後の「請求月変更」による手動補正は既に可能。
- 設定内容の設計候補: 締め日（末日を含む）と、その期間を何月分に割り当てるかを設定し、具体的な日付例で結果を確認できるようにする。初期値は現行ルールを維持する。
- 未決定事項: 個人設定の保存範囲（Windows利用者単位か台帳単位か）、工事ごとの例外の要否、設定変更の適用開始時点を決める。請求月と原価へ反映する月の関係は承認フローの計上条件と合わせて整理し、送信済み・承認済み等の状態とは区別する。
- 既存データの扱い: 設定保存だけで過去の請求月を一括変更しない。既存請求への再適用が必要な場合は対象・変更前後を確認し、バックアップして実行する設計とする。手動補正した請求月は保護する。
- 完了条件: 締め日の前後、月末、年越し、うるう年でも設定どおりに判定され、取込プレビュー・保存結果・一覧・月別集計が一致する。既存データへの適用範囲を利用者が把握できる。

### 取得速度とサーバー負荷の方針

- 利用者の最新指定に従い、**通常の取得速度は維持し、余分な待ち時間は追加しません**。既存の並列取得を一律に1件ずつへ落とす方針は採りません。
- 不要な全件取得、同じ請求の重複取得、失敗後の連続リトライを避け、総アクセス件数を抑えます。
- 比較試験では、同じ表示で受信済みのデータを利用する設計を優先します。比較のために同じ請求を二重に開かないようにします。
- アクセス制限や継続的な通信エラーが発生したら中断します。新しい回数制限・中断制御を実装済みという意味ではなく、今後の試験・実装方針です。

## 正確さ・運用に関する個別課題

### 1. 税抜額の基準を画面・集計で統一する

- 確認済み不具合: 請求書本体は税込額を10%で逆算する一方、振分行は指定した税率で計算する。
- 例: 税込1,080円を税抜1,000円・8%で振り分けても、請求一覧側の税抜は981円になる。
- 作業: 税内訳を保持するか、振分完了時は振分税抜合計を用いる。未確定の10%逆算値は明示する。Excel出力の税率・税額の扱いは、既存の出力仕様凍結との整合を確認して決める。
- 完了条件: 10%・8%・非課税・混在税率で一覧、振分、集計の説明と金額が一致する。
- 根拠: [請求書リポジトリ](../invoice_manager/repositories.py) の `insert_invoice` / `get_summary`、[金額計算](../invoice_manager/utils/money_utils.py)。

### 2. 誤請求の除外を実績・候補にも反映する

- 確認済みの挙動: 新着画面で除外しても、同じ請求がWebで保管済みになれば実績・候補へ取り込まれ得る。
- 注意点: 「ローカルには取り込まない正当な請求」と「誤請求」を一律に除外すると正しい実績も消える。
- 作業: 取込対象外と実績対象外を明示的に分け、誤請求の除外状態を実績・候補・予算へ共通適用する。
- 完了条件: 誤請求はどの集計にも含まれず、単なる取込対象外の正当な実績は保持できる。
- 根拠: [新着同期](../invoice_manager/services/digital_billder_sync.py) の `set_excluded`、[履歴集計](../invoice_manager/services/historical_costs.py)。

### 3. Web工種対応の入力ミスを「実績0円」と扱わない

- 確認済み不具合: 履歴同期が一度成功した後、予算行のWeb工種対応に存在未確認のコードを入力すると、実績が0円として扱われる。
- 影響: 行の最終原価見込が実際より低く見える可能性がある。未対応実績が別に存在する場合は全体見込を止める処理があるが、誤入力そのものは検出されない。
- 作業: コード存在と対応の検証状態を保持し、「確認済みで支出0」と「未検証」を区別する。
- 完了条件: 誤字・未確認コードで最終原価を確定表示しない。
- 根拠: [予算サービス](../invoice_manager/services/project_budget.py) の `build_project_forecast`、[予算画面](../invoice_manager/ui/project_budget_window.py) の `_actual_code`。

### 4. 履歴の鮮度、中止、失敗記録を整える

- 確認済み不具合: 通常更新で詳細を再取得せずキャッシュを使った場合も、詳細取得日時 `fetched_at` が更新される。
- 現行の制約: 請求一覧の金額・会社・日付等が同じまま査定だけ変更された場合、通常更新では分からず全件再検証が必要。
- 実装不足: 全件再検証の中止、最終試行の失敗記録、予算画面への実績取得日時の表示がない。
- 作業: 一覧確認日時と詳細取得日時を分離し、実績の時点を画面へ表示する。中止と進捗・失敗状態の保存を追加し、期限を過ぎた明細だけ再検証できるようにする。
- 完了条件: 古い査定が新しい取得結果に見えず、中止しても最後に成功した履歴が保たれる。
- 根拠: [Web読取サービス](../invoice_manager/services/web_invoice_reader.py)、[履歴集計サービス](../invoice_manager/services/historical_costs.py)、[予算画面](../invoice_manager/ui/project_budget_window.py)。

### 5. PDFの種類が増えた場合の確認を強くする

- 現行仕様: 指定どおり2ページ目を抽出する。コード体系は固定せずセル構造・見出しを使う。
- 今回の改善: 抽出候補をまとめて予算行へ追加し、複数行の集計対象を設定して一括保存できる。既存の手修正値を上書きしない。
- 残る制約: 親集計と明細の同時集計や原本総額との一致は利用者確認に依存する。OCR、別ページ選択、複数ページ取込は未対応。
- 一括追加の制約: 抽出候補に金額空欄が1件でもあると、その一括追加全体を止める。金額のある候補だけ選んで追加するか、空欄候補を個別に編集する必要がある。金額を推測で0円に補う処理はない。
- 作業: 帳票が増えた段階でページ選択、親子・小計区分、原本総額との照合を追加する。推測した階層は利用者が修正可能にする。
- 完了条件: 異なるコード・列配置でも候補をレビューでき、二重計上や総額不一致を保存前に発見できる。
- 操作方法: [工事予算・最終原価見込](PROJECT_BUDGET.md)。

### 6. 編集可能な試験請求でWeb保存を実装・検証する

- 未完了理由: 利用可能な請求が支払・保管済みで、編集可能な試験請求がまだない。
- 作業: 実編集画面の構造を確認し、承認済み構造を設定。対象ID・工事・会社・金額と差分を再検証し、「編集を保存」まで接続する。
- 完了条件: 10%・8%・非課税、既存振分あり、構造変更、途中失敗を検証する。構造不一致では永続凍結し、上司へ送る「次に回す」は実行しない。
- 引継ぎ: [Web振分の実装メモ](WEB_ALLOCATION_HANDOFF.md)。
