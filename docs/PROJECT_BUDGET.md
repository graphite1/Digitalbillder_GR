# 工事予算・最終原価見込

工事ごとの実行予算を税抜で保存し、Digital Billderから取得した保管済み実績と、利用者が入力した残工事見込を並べて確認する機能です。

## 原本PDFからの登録

画面で工事を選び、`PDF原本を確認`から実行予算内訳書を選択します。標準では2ページ目の罫線表を読み、セル構造から次の値を確認候補として表示します。

- 原本コード
- 科目
- 実行予算
- 予定金額
- 表番号と行番号

コードの文字列やコード体系は固定していません。罫線表の中で、隣り合う実行予算・予定金額の数値列と、その左側のコード・科目列を構造から探します。このため、新しいコードや英数字を含むコードも候補にできます。

抽出した候補は、次の操作でまとめて登録できます。

1. `全候補を予算行へ追加` を押します。必要な候補だけを複数選択して、`選択候補をまとめて追加` することもできます。
2. 下の予算行で集計に使う明細を複数選択し、`選択行を集計に含める` を押します。Ctrl・Shiftで複数選択でき、`全行を選択` も使えます。親集計・小計を含めないよう、対象行数と税抜合計を確認します。
3. `予算を保存` を押し、保存行数・集計対象・合計を確認すると、全行を一括保存します。集計から外した参考行も保存されます。

候補追加の段階では未保存です。既存と同じコードは上書きせず、手動修正した値やWeb工種対応を保持します。候補内のコード重複や必須金額・名称の不足があれば、その一括追加を止めます。該当候補を個別に編集するか、確認できた候補だけを選択して追加できます。

候補や予算行をダブルクリックすると編集欄へ移り、原本を見ながらコード、科目、実行予算、予定金額を修正できます。金額が空欄の候補は金額を入力してから行を登録します。表を読み取れないPDFは手入力します。

提供された帳票で、2ページ目が左右に並ぶ `コード / 科目 / 実行予算 / 予定金額 / 備考` の表であることを確認しました。上部には親集計とその明細が並び、下部には材料・外注などの詳細行と説明欄があります。実データの工事名や金額はテストデータやこの文書へ保存していません。

親集計と明細の両方を合計すると二重計上になります。一括追加した行は初めは集計対象外にし、対象をまとめて指定するか、各行の `この行を予算合計へ含める` を利用者が選びます。少なくとも1行を集計対象にしないと保存できません。小計・総計のようにコードがない行は候補にしません。表の階層が不明な場合、アプリは親子関係を推測して確定しません。

原本PDFは変更しません。保存時に `data/budgets/project-<工事ID>/` 配下へ内容ハッシュ付きの名前で複製します。同じ内容の原本は同じ保存先を再利用します。DBにはデータ領域からの相対パスを保存し、絶対パスと `..` による領域外参照を拒否します。

Excel (`.xlsx` / `.xlsm`) は内容プレビューと原本保管だけに対応します。Excelのセルから予算行を自動提案しないため、原本を確認して手入力します。`.xls` は対象外です。

## 登録後の修正と原本値

保存済み行は画面を開き直しても編集できます。現在値として、コード、科目、実行予算、予定金額、残工事見込、集計対象、Web工種対応を保持します。更新のたびに行の編集版数と編集日時を更新します。

保存済み行は行IDで追跡します。コードを変更しても同じ行として更新するため、抽出時原本値、原本候補ID、編集版数を引き継ぎます。2行のコードを入れ替える編集にも対応します。

PDFから選んだ行は、抽出時のコード、科目、実行予算、予定金額、ページ、表・行位置をJSONで保持し、原本単位の候補IDへ結び付けます。現在値を変更しても、この原本値と候補IDは書き換えません。画面の `抽出時の原本値` 列で現在値と見比べられます。原本単位の抽出候補一式も内容ハッシュ・ページごとに追記し、同じ原本の候補を上書きしません。

原本コードとWeb工種コードは別の値です。たとえば、文字列が似ていても自動では対応付けません。`Web工種対応` で履歴に存在する工種を選ぶか、コードを入力します。同じWeb工種を複数の予算行へ割り当てると実績を二重計上するため、保存時に拒否します。対応がないWeb実績は `予算行との対応未設定` として別に表示します。

## 最終原価見込

最終原価見込は次の税抜計算です。

```text
最終原価見込 = Digital Billder保管済み実績 + 残工事見込
予算差 = 実行予算 - 最終原価見込
```

実績には `historical_costs.list_actual_costs(project_id)` の `web_archived_actual` だけを使います。ローカルの請求書振分予定は実績へ加えないため、Web保管済み実績との二重計上を避けます。履歴同期の成功日時がまだない場合、実績を0円とはみなさず `未入力` とします。同期完了後は、明示的に対応付けたWeb工種に実績行がない場合だけ0円と判断します。

残工事見込の空欄は0円へ置き換えません。空欄がある行の最終原価見込と予算差は `未入力` のままです。工事が完了して残工事がない場合は、利用者が明示的に `0` を入力します。

画面右下の図は、集計対象にした予算行の構成を色分けし、最終原価見込を実績と残工事見込の積み上げで表示します。実績未同期、Web工種対応未設定、残工事見込未入力のいずれかが1行でもあれば、誤解を避けるため最終見込の棒を描きません。対応未設定のWeb実績は表に残し、件数と税抜合計を図に表示して全体見込を未確定にします。

保存ボタンを押すと、集計対象の行数、コード、実行予算税抜合計を確認画面に表示します。親集計と明細を同時に含めていないこと、原本の合計と一致することを利用者が確認してから保存します。

## サービスAPI

- `preview_source_document(path, page_number=2)`: PDFの罫線表からレビュー候補を返します。DBは変更しません。
- `prepare_budget_rows_from_candidates(candidates, ...)`: 候補を一括で未保存の予算行へ変換します。既存コードは保持し、入力不備・候補内の重複は一括追加前に検出します。残工事見込・Web対応は未設定、集計対象は未選択で返します。
- `save_project_budget(project_id, rows, confirmed=True, ...)`: 確認・編集済み行を工事単位で保存します。`confirmed=True` が必須です。
- `get_project_budget(project_id)`: 保存済み予算、現在行、原本値、編集版数を返します。
- `list_source_proposals(project_id)`: 上書きされない原本抽出候補を返します。
- `build_project_forecast(project_id)`: 明示されたWeb工種対応だけで税抜実績と最終見込を計算します。

画面の起動シグネチャは `ProjectBudgetWindow(master, project_id=None)` です。

## 読取限界

- 画像だけのスキャンPDFにはOCRを行いません。候補が出ない場合は手入力します。
- 罫線がない表、結合セルが大きく異なる帳票、実行予算と予定金額が隣接しない帳票は候補を抽出できないことがあります。
- セル内のフォント情報が壊れているPDFでは科目名を復元できないことがあります。コードと金額だけが読めた場合も、科目名を手入力してから登録します。
- 初期調整は提供された1種類の2ページ目で行いました。帳票種類が増えた場合は、実物で罫線・セル構造と候補行を確認し、固定コード表に依存せず構造判定を追加します。
- 抽出候補の表示順はPDF内の表と列の検出順です。表示順だけで親子関係を判断しません。
- 読める見出しがある場合は `実行予算` と `予定金額` の名前を優先して列を決めます。見出しを読めない場合だけ隣接する数値列から推定し、画面で列対応の確認警告を出します。
- 同じ原本コードが複数箇所にある場合は候補を統合しません。各候補の表・行位置と原本値を表示し、利用者が登録する方を選びます。
