# v1.0.8 新着81件一括取込停止の調査

## 追加の改修・検証（v1完成版へ向けて開発中）

- 以下で改善案とした選択解除・期待行数を確認する待機・原因別数値診断を実装した。初回ページは2回連続で行数と表示が一致してから容量を確定する。ページ全行が対象の場合はヘッダー1回で選び、各ページのPDF照合完了時に実件数の進捗を表示する。
- 実Web81件の全選択を修正中の取得関数で検証し、50件・31件それぞれの選択CSVが期待するID・内容と完全一致した。PDF取得部分だけ合成ZIPへ置き換え、実PDFダウンロードは0件、実台帳のハッシュ不変。結果は `作業補助/読取り試験/all-selection-controls-20260907T095433Z/result.json`。CSV等の一時ファイルは試験終了時に削除した。
- 合成試験では全81件選択、先頭ページ対象なし、部分選択解除、旧50行から新31行への遅延、解除の遅延、永続不整合、行数変化、URL逸脱、中断を検証。81件全選択のチェック操作は選択2回とページ間解除1回となる。
- この結果は改修した制御の検証であり、利用者の失敗時の根因確定や、81件分の実PDFを取得・実台帳へ登録した結果ではない。旧版の報告原因は引き続き未確定。以下の「未実装」は調査時点の履歴。

## 利用者の報告と結論

2026-09-07、候補81件を全選択して取り込むと「請求一覧の件数または選択状態を確認できません。」で停止した。画像の経過時間は23秒。原因は未確定。こちらの実Web試験では、PDF取得を省いた全選択・選択CSV取得・ページ移動は正常だった。重複登録が原因という証拠はない。

例外は台帳登録より前に発生する。ただし2ページ目以降で止まった場合、前ページ分のPDFを一時取得していた可能性があるため、「PDFを一切取得していない」とは断定しない。

## 確認した実装上の問題

- `download_selected_zip` の同じ例外に、行数0以下、チェック残存、CSV総件数を超える累計行数の3条件がまとめられている。失敗したページと実際の値が残らず、利用者の画像から原因を切り分けられない。
- ページ移動前に選択を解除せず、Web側の自動解除に依存している。今回の実Web試験では解除されたが、利用者の失敗時にも解除されたという証拠はない。
- `_wait_rows` は一覧内テキストが変われば次ページの準備完了とする。期待行数やチェック解除の完了までは確認しない。合成状態で「ページ表示だけ変化し、旧50行が残る」と待機を抜け、次の判定で `50+50>81` として停止することを確認した。これは成立する失敗経路であり、利用者環境でこの状態が発生したと確定したものではない。
- 従来の実Web試験は各ページ1件の選択だった。単体テストの疑似一覧もヘッダーの全選択状態や遅延描画を再現しておらず、全選択の状態遷移に検証不足があった。

## 読取り専用の実Web試験

1. 一覧CSV81件、1ページ目50行（チェック欄51個）。行を個別に全選択するとヘッダーも選択済み。次ページは31行（チェック欄32個）となり、ヘッダー・行とも未選択だった。500ms後も同じ。
2. 同じ81件で、ブラウザーのCPU処理を6倍に減速する条件を追加。1ページ目50件の選択CSVを取得し、対象ID・内容を検証してから次ページへ進んだ。結果は1と同じで、今回の停止条件を満たさなかった。実際のLatitudeと同じ性能・通信状況を再現した試験ではない。

両試験ともPDFのダウンロードは0件、実台帳のSHA256は前後一致。CSVと診断結果はGit対象外の `作業補助/読取り試験/selection-diagnostic-20260907T094326Z/` と `selection-diagnostic-20260907T094447Z/` に保持。請求ID・金額・認証情報を本書やGitへ含めない。こちらで稼働中の利用アプリを確認できず、利用PCでの失敗時状態は未取得。
